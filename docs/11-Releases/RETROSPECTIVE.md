## Purpose

This document captures lessons learned from the release cycle. It should focus on what worked, what did not, and what should change before the next milestone or release.

## Scope

### In scope

- Process lessons.
- Documentation gaps.
- Validation gaps and improvements.
- Recommendations for the next cycle.

### Out of scope

- Personal performance review.
- Blame assignment.
- Future release claims not supported by evidence.

## Retrospective structure

| Section | Purpose |
| --- | --- |
| What went well | Successful decisions, workflows, or validations |
| What did not go well | Problems, delays, or missed evidence |
| What we learned | Useful takeaways for the next cycle |
| What we will change | Concrete next-step improvements |
| Open follow-ups | Outstanding items and owners |

## Retrospective rules

- Focus on process and evidence, not blame.
- Tie lessons to the relevant documents or validation steps.
- Keep action items concrete and reviewable.
- Use the retrospective to improve the next milestone, not to rewrite history.

## Acceptance criteria

- [ ] The retrospective captures process and evidence lessons.
- [ ] The recommendations are concrete and actionable.
- [ ] The notes can inform the next milestone or release.
- [ ] AI Context is current.

## Open questions

- [ ] Which retrospective findings should become roadmap items?
- [ ] How should unresolved release issues be tracked after the retrospective?
- [ ] Should each major release get a separate retrospective document or a living record?
